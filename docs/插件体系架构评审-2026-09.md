# DeskBox 插件体系架构评审

- **评审日期**：2026-09-10
- **评审对象**：`official-widget-packages-plan.md`（当前执行依据）+ `pluginization-roadmap.md`（历史技术分析）+ `src/DeskBox/Services/Plugins/` + `src/DeskBox.GlancePackage/`
- **对比来源**：微软官方文档（MSIX Optional Packages、XamlReader、XBF2 性能）、竞品公开数据、仓库实测数据

---

## 一、执行摘要

**方案的技术严谨度属于专业水准，但它正在把产品推向一个可能不可逆的成本结构。**

| 维度       | 评价                                  |
| -------- | ----------------------------------- |
| 安全工程     | **9.5 / 10** — 显著高于同类项目，甚至高于多数商业产品  |
| 架构自洽性    | **9.0 / 10** — 分层清晰、约束诚实、每轮评审都有对码核实 |
| 技术选型正确性  | **7.0 / 10** — 在给定约束下合理，但约束本身值得重新审视 |
| 成本收益比    | **4.0 / 10** — **最大问题所在**           |
| 单人可维护持续性 | **4.5 / 10** — 已投入约 7,000 行只迁移了一个功能 |

**核心结论**：安全与架构设计没有问题。**问题在于"把六功能拆成进程内 NativeAOT DLL"这个目标本身，其收益可能远小于代价，而支撑决策的关键数据（多包内存开销）至今未测。**

**最紧迫动作**：在批次 D（六功能迁移）启动前，先测出"+1 个原生包"的真实内存开销。这个数字可以直接决定方案是否成立，成本不到一天。

## 二、方案做得极好的部分

必须首先明确：这是一份高质量工程文档，不是草率设计。

### 2.1 安全工程达到专业水准

以下每一条都是真实攻击面，且都被发现并修复：

| 问题                                                     | 性质                       |
| ------------------------------------------------------ | ------------------------ |
| Ed25519 弱公钥伪造（`S=1, R=B` 对任意消息通过）                      | 密码学实现级漏洞，还写了对抗测试实证攻击成立再修 |
| `[8]P` 实为 `[4]P` 小阶点漏过                                 | 同上                       |
| reparse point 穿越（`AllDirectories` 跟随 symlink/junction） | 路径穿越                     |
| IPv4-mapped IPv6（`[::ffff:127.0.0.1]`）绕过私网拒绝           | 网络边界绕过                   |
| DNS rebinding（解析后 IP 复检 + 连接 pin）                      | 网络边界绕过                   |
| 手写 URL 拆分导致"门看 A 实连 B"                                 | 校验与执行不一致                 |
| 验证器 fail-closed、分阶段停机                                  | 攻击面收敛                    |
| 重复 JSON key、safe-integer、`-0` 跨平台哈希漂移                  | 确定性哈希                    |
| TOCTOU（Runtime 只接受 `VerifiedInstalledPackage`）         | 验证与加载绑定                  |

自研 Ed25519 连续三轮产出密码学 bug 后，主动降级为 `ed25519-dalek verify_strict` 并把 C# 实现降为 test oracle——**这是正确的技术判断，很多团队会为了"已经写了"而继续硬撑。**

### 2.2 架构自洽性

- 三根分离（PackageRoot 只读 / PackageDataRoot / InstanceDataRoot）正确解决了"内容寻址安装目录 + 数据持久化"的冲突
- `InstanceStorageKey` 用 SHA256 而非实例 ID 直接当路径——路径穿越免疫
- 包代码永不于管理器锁内调用——为回调防重入预留
- HostApi 函数表带 Size/Version 头——后续扩展不抬整包 ABI
- 二十余轮审计逐条对码核实，而非纸面评审

### 2.3 诚实的约束记录

XBF/PRI/WinRT 激活三问实测为"当前不可行"并钉进回归断言，而不是假设可行继续推进。这一点很多项目做不到。

## 三、三个结构性问题

### 3.1 问题一（最严重）：多包内存开销未测，而这是方案的生死线

**已知数据**：

- 零售包总体积 **158 MB**（`.artifacts/aot-retail/win-x64/publish`）
- 单个原生包 DLL：Glance v1-v3 ≈ **6.18 MB**，Todo 包 **4.26 MB**
- `spikes/glance-native/README.md:78` 明确记录：
  > 冷启动/工作集/**多包规模化的系统测量（当前仅记录模块加载+建视图耗时与 DLL 体积）**
- `official-widget-packages-plan.md:93` 要求：
  > **内存硬数据**：Host only / +1 / +3 / +6 包加载……**批次 D 前必须有数**

**为什么这是生死线**：

NativeAOT DLL 是静态链接产物。每个包自带一份运行时代码、类型元数据、字符串池。六包加载进同一进程后：

- DLL 无法 `FreeLibrary`（NativeAOT 限制，文档已确认）→ 加载即常驻
- 每个包的 Private WS 不是 6 MB，而是 6 MB 映像 + 各自的 .data/.bss + 独立堆分配
- 保守估计单包实际占用 **15–30 MB**，六包即 **90–180 MB 额外内存**

**竞品对照**：

| 产品                | 内存占用              |
| ----------------- | ----------------- |
| Stardock Fences 6 | < 30 MB           |
| Coodesker 酷呆桌面    | 24 MB             |
| DeskBox 当前        | 需测                |
| DeskBox + 6 原生包   | **未知，可能 150 MB+** |

DeskBox 当前产品定位的一条主线就是"轻量"——竞品对比中这是明确优势，1.5.0 还在加"隐藏后裁剪工作集"这类实验性优化。**如果插件体系让内存翻几倍，等于用架构手段抹掉产品的核心卖点。**

而这件事的验证成本极低：装一个包，读一次 `Private Working Set`。**这个数字应该在迁移第二个功能之前就拿到。**

### 3.2 问题二：运行时文本 XAML 的代价被低估

文档已确认编译 XBF 在动态 AOT DLL 中不可行，因此正式路径是运行时文本 XAML。但微软文档的量化收益值得重新审视：

**XBF2 相对文本 XAML 的优势（微软官方 `optimize-xaml-loading.md`）**：

- 完全避免运行时的文本解析成本
- **完全内存映射，加载读取零 heap footprint**
- 应用可获得 **15–20% CPU**、**10–15% Win32 heap** 的改善
- 磁盘占用最多减少 **50%**
- 为 XAML 类型提供 fast-path，改善 VSM / ResourceDictionary / Styles 的堆和对象创建成本

**`XamlReader.Load` 的额外硬限制（WinUI 3 官方文档）**：

> The object that is created from Load can be assigned to only one location in the primary object tree. If you want to add objects created from identical XAML to different areas…… **you must parse the XAML multiple times** using the same input string.

**这条对 DeskBox 尤其致命**：DeskBox 支持**多实例**（Glance 多实例已实现）、**叠放**、**合并组**。每个实例都要**重新解析一次完整 XAML**。N 个 Glance 实例 = N 次文本解析 + N 份对象树。

叠加的代价还有：

| 项           | 代价                                                            |
| ----------- | ------------------------------------------------------------- |
| code-behind | 官方明令"cannot integrate with code-behind"，全部事件改 `FindName` 手动订阅 |
| 本地化         | 无 PRI，包须自带 `strings/*.json` + 回退链                             |
| 主题          | 无 `ThemeResource` 自动响应，须 HostApi token 注入 + 手动替换资源字典          |
| 转换器         | 包 XAML 无转换器（已记录），须宿主侧预计算或包内重写                                 |

**净效果**：每迁移一个功能，不是"搬代码"，而是**用一套能力更弱、性能更差的 UI 管线重写一遍**。这解释了为什么 Glance 一个功能就花了 3,110 行包代码 + 二十余轮审计。

### 3.3 问题三：成本收益比失衡

**已投入**（截至评审日）：

| 项                        | 规模                                                                               |
| ------------------------ | -------------------------------------------------------------------------------- |
| `Services/Plugins/`      | 16 文件 / 3,971 行（`PluginPackageVerifier` 1,384 + `NativeWidgetPackageLoader` 925） |
| `DeskBox.GlancePackage/` | 3,110 行                                                                          |
| 相关测试                     | 31 个测试文件                                                                         |
| 评审轮次                     | 20+ 轮                                                                            |
| **已迁移功能**                | **1 / 6**                                                                        |

**剩余工作量**（按 `quickcapture` 最重、`music` 最轻估算，取 Glance 为中位数）：

3,110 行/功能 × 5 ≈ **15,500 行**，加上基础设施演进，总量约 **25,000 行**。

**收益侧**：

158 MB 零售包中，绝大部分是 Windows App Runtime + WinUI 运行时（宿主无论如何都要带），功能代码只占一小部分。即使六功能全拆：

- 基础包可能仍在 **120 MB** 量级
- 按需安装节省约 **20–35 MB**（用户只装 1–2 个功能时）

**用 25,000 行重写 + 性能损失 + 内存风险，换 20–35 MB 的安装包缩减。**

如果这个交换成立，前提是"安装包体积"是当前产品的主要痛点。**但我没有在仓库中找到支撑这一判断的用户反馈或数据。** 相反，README 与 CHANGELOG 显示用户关注的重点是稳定性、内存、DPI、多显示器——**这些恰恰是插件体系会恶化而非改善的维度。**

## 四、替代方案对比

| 方案                            | 迁移成本    | 性能                 | 内存        | 包体收益     | 生态能力        | 评价                                                                                                                                                        |
| ----------------------------- | ------- | ------------------ | --------- | -------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 当前：进程内 NativeAOT DLL**   | 极高（全重写） | 中（运行时 XAML）        | **高风险未测** | 20–35 MB | 强           | 已投入最多，风险最大                                                                                                                                                |
| **B. 进程外 exe + IPC**          | 极高      | 低（IPC + 跨进程 UI 寄宿） | 高（每进程）    | 同 A      | 强 + 可热更新/卸载 | WinUI 跨进程寄宿难度高于 A                                                                                                                                         |
| **C. 只做增量包，不迁移现有六功能**         | **零**   | **最优（保留编译 XBF）**   | **无增加**   | 0        | 保留（新功能/第三方） | **收益最小但风险也最小**                                                                                                                                            |
| **D. 功能开关 + 按需下载资源**          | 低       | 最优                 | 无增加       | 有限       | 无           | 解决包体但不解决独立演进                                                                                                                                              |
| **E. MSIX Optional Packages** | —       | —                  | —         | —        | —           | **需 Store 特别许可**，且 Store 政策 10.1.5 限制外部下载；官方文档明确"To submit an app that uses optional packages and/or related sets to the Store, you will need permission" |

**关于 E 的补充说明**：搜索确认 MSIX 可选包含可执行代码时必须属 related set，且上架 Store **需要微软特别许可**。同时有实测报告指出 MSIX 虚拟化层会让 WinUI 3 文件操作慢 2–3×（MSIX filter driver 导致额外 `IRP_MJ_CREATE`）。文档中对 E 的排除判断是**正确的**。

## 五、建议

### 5.1 立即执行（1 天内）

**测量单包内存开销。** 不需要完整矩阵，最小充分数据：

```
Host only（无包加载）           → Private WS / Commit / mapped image
+1 个原生包（Glance）激活       → Private WS / Commit / mapped image
+1 个包，创建 3 个实例          → 同上（验证 XamlReader 多实例重复解析的代价）
+1 个包，视图全销毁但 DLL 常驻  → 同上（验证"卸载不释放"的长期占用）
```

判定标准建议：

- 若 +1 包增量 **< 10 MB** → 方案可行，继续批次 D
- 若 +1 包增量 **10–20 MB** → 六包将增 60–120 MB，需重新评估，考虑只迁移 2–3 个轻量功能
- 若 +1 包增量 **> 20 MB** → **方案不成立**，转向方案 C

### 5.2 短期决策（拿到数据后）

**如果数据不好看，我建议转向方案 C：只做增量包，不迁移现有六功能。**

理由：

1. **现有六功能保留编译 XBF** — 零性能损失，零重写成本，15,500 行工作量直接消失
2. **插件基础设施不浪费** — B1 验证管线、PackageManager、签名、HostApi 全部保留，用于新功能和第三方
3. **产品目标可调整** — "按需安装"改为"新功能按需安装"，用户认知上完全成立
4. **内存与性能不劣化** — 保住相对 Fences / Coodesker 的轻量优势

代价只是"安装包不会变小 20–35 MB"，而这是三个选项中代价最小的一个。

### 5.3 如果坚持方案 A

那么在批次 D 之前，建议追加三项硬门槛：

1. **内存矩阵必须有数**（Host / +1 / +3 / +6），否则不启动第二个功能迁移
2. **先迁移 Music 而非顺序中的下一个**（计划中顺序为 Glance→Music→Search→Weather→Todo→QuickCapture）——Music 3 字段最轻，且已在阶段 2 做过 per-kind store 试点，能最快暴露"第二个包"的真实成本
3. **设定退出判据**：如果前三个功能迁移后内存增量超过阈值（建议 60 MB），暂停并重新评估，而不是"已经做了三个所以继续"

### 5.4 关于 QuickCapture

计划把它排在最后（"最重交互最后"）是对的。但需要明确：**QuickCapture 涉及 CommunityToolkit 控件、拖放、KeyDown、宿主自定义控件、局部转换器**，probe 已确认这些在包 XAML 中可解析但需手动接线。它的迁移成本可能不是 Glance 的 1 倍，而是 2–3 倍。

**建议在动它之前先算清楚**：如果这个功能的迁移成本高于重新审视整个方案的成本，那就不该迁。

## 六、一个更根本的问题

`official-widget-packages-plan.md` 开头写明产品目标是"六功能按需安装、独立更新"。

但在整个仓库中，我没有找到支撑这个目标的**用户侧证据**：没有 issue 引用、没有反馈汇总、没有"安装包太大"的投诉记录。相反，CHANGELOG 中 1.5.0 的 20 条修复几乎全部是稳定性与边界正确性，1.4.7 以来的性能工作集中在内存与响应速度。

**如果这个目标来自"技术上应该这样做"而非"用户需要这个"，那么它值得被重新审视。**

插件体系的真正价值通常有三类：① 减小分发体积；② 让第三方扩展；③ 隔离故障域。DeskBox 的 ①收益有限（20–35 MB）、③对官方可信包无意义（本来就同进程全信任）、**只有 ② 是真实且长远的**。

而 ② 恰恰**不需要迁移现有六功能**——它只需要一套稳定的包格式和能力接口，让新功能（无论是官方还是第三方）可以增量加入。

这正是方案 C 的全部内容，成本约为方案 A 的 5%。

## 七、总结

| 判断           | 结论                                      |
| ------------ | --------------------------------------- |
| 安全工程是否有问题    | **没有**，达到专业水准                           |
| 架构设计是否自洽     | **是**，分层与约束诚实，每轮有对码核实                   |
| 技术选型是否合理     | **在给定约束下合理**，但 XBF 不可用导致的运行时 XAML 代价被低估 |
| **目标本身是否合理** | **存疑**，成本收益比失衡，且缺用户侧证据                  |
| **最大风险**     | **多包内存开销未测，而这直接决定方案生死**                 |
| **最紧迫动作**    | **测 +1 包的内存增量，1 天内可完成**                 |

这套体系的设计质量配得上更好的目标。**在投入 15,500 行迁移剩余五个功能之前，值得先花一天确认地基承不承受得住。**
